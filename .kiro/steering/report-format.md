# レポート表記とテストリンクの規約

## 規約

### 要件ID
- 形式は `R-NN`（接頭辞は大文字、番号は2桁ゼロ埋め）。例: `R-01`, `R-42`。
- `r01` や `R1` のような表記は、内部で必ず `R-01` に**正規化してから**扱う。

### テストと要件のリンク宣言（3方式）
テスト側から要件IDを宣言する方法は次の3つを認める。ears-trace はこの3方式を拾う。

```python
import pytest


# 1. マーカー（推奨）
@pytest.mark.requirement("R-02")
def test_invalid_form_shows_errors() -> None: ...


# 2. 命名規約（test_r02_... -> R-02）
def test_r02_invalid_form() -> None: ...


# 3. docstring 内のタグ
def test_server_side_validation() -> None:
    """req: R-08"""
```

- テストIDは `モジュール名::テスト関数名` 形式で生成する（クラス内メソッドは対象外）。

### HTMLレポート
- 外部リソースに依存しない**自己完結の静的HTML**（インラインCSS）で出力する。
- 要件原文・テストIDなど**入力由来の文字列は必ずHTMLエスケープ**する。
- レポートには**入力のSHA-256ハッシュ**と**生成時刻（UTC, ISO 8601）**を埋め込む。

## 意図（なぜこの規約か）

- **ID正規化を怠ると同一要件が別物として二重計上される**。`R-1` と `R-01` が別IDになると
  カバレッジ率が壊れる。境界（リンク抽出時）で正規化して以降は正規形だけを流す。
- リンク方式を3つ許すのは、既存プロジェクトのテスト記法に後付けで適用できるようにするため。
  ただし生成するスタブは方式1+3を必ず付け、**自ツールで再リンク可能**にする（自己整合）。
- ハッシュと生成時刻を埋めるのは、レポートが「その入力から今まさに生成された」ことを示す
  証跡のため。静的モックとの区別、デモでのライブ生成の裏付けになる。
- HTMLエスケープは XSS と表崩れの防止。入力は信頼しない（外部データとして扱う）。

## コード例

```python
# 良い例: 抽出したIDは即正規化する
def normalize_id(raw: str) -> str:
    m = re.match(r"^([A-Za-z]{1,5})-?(\d{1,4})$", raw)
    prefix, num = m.group(1).upper(), int(m.group(2))
    return f"{prefix}-{num:02d}"  # "r1" -> "R-01"


# 良い例: 入力由来の文字列はエスケープしてから描画
cell = html.escape(requirement.text)

# 悪い例: 生の文字列をHTMLに直接埋める（XSS・表崩れ）
cell = requirement.text  # ← 禁止
```
